# Качество: протокол проверки детектора

Качество определяется на **всей цепочке**: frontend, модель, порог,
подтверждение, cooldown, при наличии — энергетический гейт. Высокая
accuracy на отдельных клипах не является критерием готовности устройства.

## 1. Область обещаний V1

Любой человек, перечисленные микрофоны, расстояния и условия шума.
Обещание проверяется только на живых людях, которых нет в train
(`dataset/holdout/`), с результатом по каждому человеку: среднее по всем
может скрыть провал на детях, шёпоте или акценте. «Гермес» внутри фразы считается целевым словом. Упоминание имени или
произнесение слова телевизором — вопросы постановки задачи, не автоматически
ошибки акустической модели. Контракт фиксируется до сбора данных (L0).

| Показатель | Цель | Что публикуем |
|---|---|---|
| Event recall | ≥95% | Обнаруженные/все произнесения, интервал, условия |
| False accepts/hour | ≤0.1 | Число ложных событий / длительность негативного потока |
| Похожие слова | 0 наблюдаемых событий на 500 попыток | 0/500 не означает нулевой истинный риск |
| Задержка | ≤500 мс после конца слова | Доли в бюджете, p50/p95 и максимум для обнаруженных |
| Время шага | Укладывается в период 100 мс с запасом | Измерения полной цепочки под нагрузкой |
| RAM, flash, ток | В бюджете выбранного устройства | Измерения сборки, режим питания и периферия |

Различай «наблюдаемое значение достигло цели» и «верхняя/нижняя
доверительная граница подтверждает цель». Для строгого заявления
recall ≥95% нужна нижняя граница ≥95%; один результат 95/100 этого не доказывает.

## 2. Наборы данных

| Набор | Назначение | Можно принимать решения по результату? |
|---|---|---|
| Train | Обновление весов, аугментации | Да |
| Clip val | Диагностика loss и ошибок, выбор checkpoint | Да |
| Development streams | Выбор порога, K, cooldown, frontend | Да |
| Final positive streams | Отдельные сессии с размеченными словами | Только итоговая оценка |
| Final ambient | Отдельные записи без целевого слова | Только итоговая оценка |
| Final confusables | Независимые записи похожих слов | Только итоговая оценка |

Источники final не используются ни для аугментаций, ни для подбора
гиперпараметров. Если после final переделал систему по увиденным ошибкам,
этот набор становится development; для новой независимой оценки нужен
новый holdout. Не собирай трудные негативы из финального теста по кругу.

На каждый набор сохрани manifest, разметку, checksum и часы/число событий.
Повторы в одной комнате не равны независимым условиям. Отчёт разбивай по
шуму, микрофону, дню и диктору, чтобы среднее не скрывало провал.

## 3. Что реализовано

- `make eval` — кривая порогов на клипах val.
- `make eval SPLIT=test` — кривая на текущем test; используй только строку
  заранее выбранного порога, не ищи новый оптимум на test.
- `make score DIR=... T=...` — score файлов; метки и события не сопоставляет.
- `make stream FILE=... HOP=100` — FA/h для нескольких порогов на длинном
  PCM16 16kHz WAV **без слова**; K=2 и cooldown приблизительно 2с.

Окна перекрываются. При шаге 100 мс за 10 часов получается около 360 тысяч
оценок, а не 30 тысяч независимых испытаний. После подтверждения/cooldown
ошибочные окна объединяются в события. Пересчитывать clip FPR в FA/h
простым умножением нельзя.

Автоматические event recall, сопоставление с разметкой и задержки пока
не реализованы — это лабораторная L7. До её выполнения отчёт по потоку
с позитивами нужно вести отдельно; `make stream` считает все события
ложными и для такого файла не подходит как оценка FA/h.

Энергетического гейта в текущем `eval stream` нет. Добавление его только
в прошивку изменит систему. Сначала одинаковая реализация в обеих средах,
затем повторная оценка, включая тихое слово и тихие негативы.

## 4. Правила событийной оценки (реализовать в L7)

Разметка позитивной записи: CSV `start_s,end_s`, одна строка на целевое
произнесение. Время det — конец входного окна плюс фактическое время
вычисления на устройстве. В offline-прогоне отдельно указывай, что
вычислительная задержка ещё не учтена.

Для каждого произнесения разрешён интервал `[start_s, end_s+0.5]`.
Одно событие сопоставляется максимум с одним словом, одно слово — максимум
с одним событием. Для непересекающихся интервалов сопоставляй по времени;
для пересечений используй заранее зафиксированное однозначное one-to-one
правило и отдельный тест близких обращений.

- Сопоставленное событие — TP; слово без события — FN.
- Несопоставленное событие — FP, в том числе повторное срабатывание.
- Задержка `det−end_s` может быть отрицательной; не обрезай её до нуля.
- Основной FA/h измеряй на отдельном потоке без слов; FP смешанного
  потока публикуй отдельно с его длительностью.
- Публикуй event recall, задержки обнаруженных и долю всех слов,
  обнаруженных в бюджете. Нельзя скрыть пропуски хорошей задержкой TP.

Проверь startup, слово на границе окна, слово внутри связной речи,
два обращения ближе cooldown, шум, молчание, длинное похожее слово.
Реальный поток во время cooldown продолжает поступать в кольцевой буфер.

## 5. Выбор рабочей точки

На development-потоке перебери порог при фиксированных K и cooldown.
Сравни event recall и FA/h. При необходимости меняй K/cooldown отдельно,
следя за задержкой и близкими повторными обращениями. Затем заморозь
веса, frontend и всю постобработку до final-прогона.

Порог не обязан быть 0.5 или попадать в диапазон 0.7–0.9. Если ни одна
рабочая точка не удовлетворяет требованиям, изучи ошибки и данные.
Увеличивать cooldown до получения красивого FA/h без проверки recall нельзя.

Ранжирование checkpoint по val loss — начальная эвристика, а не доказательство
лучшей событийной рабочей точки. Сохраняй кандидатов для development-оценки.

## 6. Статистическая уверенность

Для k обнаруженных из n независимых произнесений используй интервал Wilson
или точный биномиальный; укажи метод. Аугментации и несколько окон одного
слова не увеличивают n независимых произнесений. Если сессии зависимы,
оцени разброс между сессиями или применяй cluster bootstrap по сессиям.

При нуле ложных событий за T часов односторонняя верхняя 95%-граница
интенсивности в стационарной пуассоновской модели:

```
lambda_upper = −ln(0.05)/T ≈ 2.996/T
```

0 за 10ч → верхняя граница около 0.30/ч.
0 за 30ч → около 0.10/ч.
1 за 10ч → наблюдаемая частота 0.10/ч, но её верхняя граница выше цели.
Формула и допущения: [NIST, zero-failure confidence bound](https://www.itl.nist.gov/div898/handbook/apr/section4/apr451.htm).
Для ненулевого числа событий нужен соответствующий пуассоновский интервал.

Это модель оценки, не гарантия для любого звука: события могут группироваться,
cooldown вводит зависимость, а интенсивность меняется между условиями.
Длинный повтор одной записи не заменяет новые часы разнообразного аудио.

## 7. Порядок доведения

1. Tiny-overfit и baseline; убедиться, что математика и метки работают.
2. Собрать development-данные своего голоса обоих классов и фон.
3. Прогнать базовую CNN, разобрать уверенные ошибки, проверить shortcut-гипотезы.
4. По одному проверить аугментации, признаки и регуляризацию.
5. Реализовать события с разметкой; выбрать рабочую точку.
6. Заморозить конфигурацию, провести final с интервалами.
7. Перенести float на устройство; проверить parity и снова событийные метрики.
8. Измерить ресурсы, затем оптимизировать и повторить проверку.

Не добавляй автоматически дельты, BatchNorm, больше слоёв или denoising.
Каждое изменение — гипотеза; шумоподавление может исказить слово,
CMVN — усилить слабые колебания, гейт — пропустить тихое обращение.

## 8. Отчёт о готовности

Версия кода/данных/весов; параметры frontend и детектора; область условий;
TP/FN/FP и часы; доверительные интервалы; задержки; RAM/flash/время/ток;
известные провалы. Числа с симуляции на Mac и измерения ESP32 разделяй.
До такого отчёта система является прототипом, даже если демонстрация удалась.
