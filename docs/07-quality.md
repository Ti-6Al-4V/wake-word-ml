# Качество: как сделать рабочую модель, а не игрушку

Это инструкция по доведению своей модели до состояния, когда кепка реально
просыпается от слова "гермес" и не просыпается от всего остального.
Методология собрана из практики Porcupine / microWakeWord / ESP-SR,
адаптирована под наш стек (Rust + burn + ручной C++ inference).

---

## 1. Критерий готовности (acceptance criteria)

Модель считается готовой, когда выполнены ВСЕ условия:

| Метрика | Цель | Как измеряем |
|---------|------|--------------|
| True positive rate (своё слово, свой голос) | ≥95% | 100 записей "гермес" своим голосом в разных условиях |
| False accepts на ambient | ≤1 в 10 часов | Прогон 10 часов подкастов/музыки/улицы без слова |
| False accepts на похожие слова | 0 на 500 попыток | "термес", "Герман", "Гермес" в составе фраз из Golos |
| Задержка детекции | ≤500 мс от конца слова | Замер на ESP32 |
| Потребление в always-on | — | Замер тока, сравнение с light sleep |
| Размер модели | ≤50 KB (q8) | После квантования |

**Главная метрика — false accepts в час.** Accuracy вторичен: модель с
accuracy 99% и ложной тревогой раз в 5 минут — нерабочая.

## 2. Данные — 80% успеха

### 2.1 Позитивы: разнообразие голосов

Текущий план (2 голоса Edge TTS + 100 своих записей) — слабое место.
Модель выучит тембр Светланы и Дмитрия, а не слово.

Целевой состав позитивов:

| Источник | Кол-во | Зачем |
|----------|--------|-------|
| Свой голос, INMP441 (как в кепке!) | 300–500 | **Основной.** Тот же микрофон = тот же спектр шума и АЧХ |
| Свой голос, телефон/ноутбук | 100 | Другой микрофон → робастность |
| Друзья/семья (если возможно) | 50–100 | Другие тембры |
| TTS: Edge (5+ русских голосов) | 300 | Синтетика, разные тембры и скорости |
| TTS: Yandex SpeechKit / Silero TTS | 200 | Другой синтезатор = другой домен |

Критично: **записывать тем же INMP441, который стоит в кепке.**
Домен сдвиг "студийный микрофон ноутбука → копеечный MEMS в кепке на улице"
убивает точность сильнее всего.

### 2.2 Негативы

| Источник | Кол-во | Зачем |
|----------|--------|-------|
| Golos (Сбер, русская речь) | 3000+ | Главный источник: живая русская речь |
| Google Speech Commands | 2000 | Короткие английские слова |
| Fonематические двойники | 200 | "термес", "Герман", "первый класс", фразы с "герм..." |
| Музыка + шум + улица | 1000 | Ambient |

Фонематические двойники — отдельный обязательный класс. Слово "гермес"
может ложно сработать на "термес", "ксермес", быстрое "гер метр". Их надо
в датасете И в отдельном тестовом наборе.

### 2.3 Аугментации

Из каждого реального позитива:
- pitch shift ±2–3 полутона
- time stretch 0.85–1.15
- шум: белый, уличный, музыкальный, SNR 5–20 dB
- реверберация (импульсы комнат, RIR-датасеты)
- громкость 0.3–1.5
- **случайный сдвиг внутри 1-сек окна** (слово не всегда в центре)

Целевой объём после аугментации: 8–15 тысяч позитивов, 10+ тысяч негативов.

## 3. Архитектура inference: стриминг вместо окон по 300 мс

Текущий дизайн (05-integration.md): кольцо из 33 кадров, проверка каждые
10 кадров (~300 мс). Проблема: слово "гермес" длится ~600–800 мс. Если оно
началось сразу после проверки, его начало уезжает из окна. Модель видит
слово в разных позициях окна → точность падает, нужен больший порог.

Правильный подход — **скользящее окно с перекрытием**:

```
Окно = 33 кадра (~1 сек). Сдвиг = 3 кадра (~90 мс).
Каждые 90 мс окно сдвигается, forward pass считается по актуальному окну.
Слово в любом положении внутри окна видится почти целиком.
```

Forward pass ~11 мс (04-deploy.md), период 90 мс → загрузка ядра ~12%.
Норм для Core 1.

Дополнительно — **энергетический гейт** перед CNN:

```
if (frame_rms < NOISE_FLOOR) skip;   // тишина → не считаем CNN вообще
else накопить кадры → CNN
```

Это экономит батарею (CNN не крутится на тишине) и снижает ложные
срабатывания на стационарном шуме.

### Пост-обработка детекции

Не срабатывать на одиночном пике. Схема подтверждения:

```
score > THRESHOLD в K подряд окнах (K=2, окна перекрываются) → детекция
после детекции: cooldown 2 сек (не ловить эхо собственного слова)
```

## 4. Оценка: правильные тесты

Стандартного train/val/test split недостаточно. Отдельные тестовые наборы:

### 4.1 Тестовые наборы

| Набор | Содержимое | Что проверяет |
|-------|------------|---------------|
| test_clean | Своё слово, чистые записи | Базовая способность |
| test_noise | Слово + шум (SNR 5, 10, 20) | Робастность |
| test_speakers | Слово голосами не из train | Обобщение на говорящих |
| ambient_10h | 10 часов: подкасты, музыка, улица, ТВ | **False accepts/hour** |
| confusables | 500 записей похожих слов/фраз | Фонематическая стойкость |

`ambient_10h` в train не входит никогда. Это симуляция жизни.

### 4.2 Прогон ambient как стриминга

Ambient-тест прогоняется **стримингово**: окно скользит с шагом 90 мс по
10-часовой записи, считается количество детекций и FPS ложных тревог:

```
false_accepts_per_hour = число детекций / часы аудио
```

### 4.3 Кривая порогов

Метрики строятся для серии порогов 0.3–0.95:

```
TPR(θ) vs FA/h(θ)
```

Рабочий порог выбирается в точке, где TPR ≥95% при FA/h ≤0.1.
Обычно это θ = 0.7–0.9. Если такой точки нет — проблема в данных или
модели, не в пороге.

## 5. Модель: что поправить в текущей архитектуре

Текущая CNN (5K параметров) — разумный старт, но:

1. **Нормализация по всему окну** (02-dataset.md, mean/std по всей матрице) —
   плохо для стриминга: среднее "плавает" при скольжении окна. Заменить на
   per-coefficient нормализацию с бегущим средним или CMVN без глобального std.

2. **Дельты**: добавить Δ и ΔΔ MFCC (первые/вторые производные по времени)
   — даёт динамику, сильно помогает различать слова. Вход станет [33 × 60].

3. **Размер**: не бояться вырасти до 30–50K параметров (~120 KB q8).
   ESP32-S3 с PSRAM это переварит, а ёмкости для разных голосов нужно больше.

4. **BatchNorm/Dropout** между слоями при обучении (dropout 0.2–0.3).

5. **Квантование**: перед деплоем — post-training quantization до int8
   (калибровка на 100–200 записях). Проверить метрики ПОСЛЕ квантования —
   на 5K параметров деградация бывает заметной.

## 6. Цикл итераций

```
1. Собрать данные v1 (свой голос + TTS + Golos)
2. Обучить, прогнать все 5 тестовых наборов
3. Смотрим на метрики:
   - FA/h высокий → больше/жёстче негативов, выше порог
   - TPR низкий на шуме → больше аугментаций шумом
   - TPR низкий на чужих голосах → больше TTS-голосов/дикторов
4. Повторить с 2
```

Целевой темп: одна полная итерация — 1 вечер. Не полировать первую модель
до блеска, а быстро крутить цикл.

## 7. Поэтапный план

### Фаза 1 — базовая модель (свой голос, тишина)
- Данные: 300 своих записей + Edge TTS + Golos негативы
- Цель: TPR ≥95% на своём голосе в тишине, FA/h ≤5
- Результат: прототип на ESP32, кепка просыпается дома

### Фаза 2 — робастность
- + шумовые аугментации, реверберация, дельты MFCC
- + ambient-тест 10 часов
- Цель: TPR ≥95% при SNR 10 dB, FA/h ≤1
- Результат: работает на улице и в кафе

### Фаза 3 — оптимизация под кепку
- + энергетический гейт, стриминг с перекрытием, int8 квантование
- Замер тока always-on режима, подбор light sleep стратегии
- Цель: потребление в always-on ≤2 мА среднего
- Результат: готовый модуль для CapAI

### Фаза 4 — A/B с microWakeWord (опционально)
- Обучить модель "гермес" в Colab через microWakeWord (Piper RU голоса)
- Сравнить FA/h и TPR со своей моделью
- Результат: уверенность, что свой путь не хуже, или готовый запасной вариант

## 8. Риски и чем крыть

| Риск | Вероятность | Митигация |
|------|-------------|-----------|
| TTS-модель не обобщится на живой голос | Высокая | Максимум реальных записей INMP441; A/B с Phase 4 |
| Ложные срабатывания от ТВ/подкастов | Средняя | ambient_10h в каждой итерации; жёсткие негативы |
| INMP441 + улица = низкий SNR | Высокая | Шумоподавление на входе (простой spectral gate) до MFCC |
| Слово бормочется неразборчиво | Средняя | Принять TPR 90% для бормотания; порог не занижать |
| burn/ручной C++ не сойдётся | Низкая | Прогнать 100 сэмплов через оба пайплайна, сравнить score побитно |

Последний пункт важно: **числа из Rust-тренировки и C++ inference должны
совпадать до 3 знака** на одних и тех же входных данных. Это первый тест
при деплое — до него мерить метрики на ESP32 бессмысленно.
